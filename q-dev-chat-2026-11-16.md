## 🔴 Priority 1 — Critical Issues

**1. Reset token returned in API response (auth.controller.js ~L110)**
```js
res.json({ success: true, resetToken, ... }); // token sent in response body
```
The password reset token is returned directly to the caller instead of being emailed. Anyone who intercepts the response (or calls the endpoint) gets a valid reset token. This needs to be sent via email only.

**2. RFQ ID collision risk (inquiries.controller.js ~L72)**
```js
const rfqId = `EE-RFQ-${Math.floor(1000 + Math.random() * 9000)}`;
```
Only 9000 possible values. With a `UNIQUE` constraint on `rfq_number`, this will throw a DB error under moderate load. Use `randomUUID()` or a sequence like warranty claims do (`EE-WC-${randomUUID().split("-")[0]}`).

**3. Memory fallback silently hides DB errors (inquiries.controller.js ~L95)**
```js
} catch (err) {
  memoryInquiries.unshift(inquiryRecord); // data lost on restart
}
```
If the DB insert fails for any reason other than missing table (e.g. constraint violation, connection drop), the inquiry silently goes to memory and is lost on server restart. At minimum, log the error and distinguish table-not-found from other errors.

**4. JWT stored in localStorage (AuthContext.js)**
Tokens in localStorage are accessible to any JS on the page (XSS risk). For a B2B platform handling orders and quotations, `httpOnly` cookies are the correct approach.

## 🔴 Priority 1 — Security (Confirmed by Scanner)

**1. SSRF risk in products/page.js (lines 31–32)**
The `fetchJson` function uses `API_BASE_URL` concatenated with user-supplied `searchParams` values to build a server-side fetch URL. If `API_BASE_URL` is not strictly validated, a crafted URL could redirect the server-side fetch to internal hosts.

Fix: validate `API_BASE_URL` is a trusted origin at startup, and never interpolate raw user input directly into the fetch URL — use `URL` + `searchParams.set()` (which the code partially does, but the base URL itself is unvalidated).
